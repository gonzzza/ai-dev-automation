# Run ready specs locally in parallel, one worktree each

## Goal
Spec 005's coordinator starts ready specs as CI runs, which need the agent's GitHub App, Actions minutes and API spend. This change lets a developer run the same plan on their machine, on their Claude subscription: each ready spec gets its own git worktree, and a headless Claude Code session implements it there, in parallel with the others. The harness still runs every gate in code (checks, scope, git state, secrets) before it commits, pushes and opens the PR, so a session run is held to the same rules as an agent run. Every run, of either kind, claims its spec on GitHub before it starts, so local and CI coordinators can run side by side without implementing a spec twice. The runs never talk to each other.

## Requirements

### Session runs
- New spec-run option `--session`: `npm run agent -- <spec.md> --session [options]`. The pipeline is the same as an agent run (preflight, claim, gates, commit, push, PR). Only the step that writes the code changes: a headless Claude Code session instead of the Agent SDK. It runs on whatever Claude Code is signed in with, so on a subscription it costs no API spend.
- `runSession(task, config, spawn)`, a new exported function in `spec-coding-agent/src/session.ts`, runs the session. It returns the same `AgentRun` as `runAgent`, so `runPipeline` takes it through its existing `runAgent` dependency. It runs, in the repository root, with no shell:

  ```
  claude -p --output-format json --json-schema <report schema> --permission-mode dontAsk
    --setting-sources project --no-session-persistence --model <model> --effort <effort>
    --max-budget-usd <max budget> --allowedTools <allowed> --disallowedTools <denied>
  ```

  - The prompt is the spec task built from `prompt.md`, as for an agent run, written to the session's stdin: with a long spec it would pass Windows' 32,767-character command-line limit. `<report schema>` is `AGENT_REPORT_JSON_SCHEMA` as a JSON string.
  - `--allowedTools`: `Read`, `Glob`, `Grep`, `Bash(npm run check)`, plus `Edit(./<dir>/**)` and `Write(./<dir>/**)` for each writable directory. `--permission-mode dontAsk` denies every other tool call instead of prompting.
  - `--disallowedTools`: `Read(**/.env)`, `Read(**/.env.*)`, `Read(**/CLAUDE.local.md)`, `Read(**/.npmrc)`, `Read(**/*.pem)`, `Read(**/*.key)`, `Read(**/*.p12)`, `Read(**/*.pfx)`, and `Bash(git *)`, `Bash(gh *)`, `WebFetch`, `WebSearch`.
  - It never passes `--bare`. `--bare` reads only `ANTHROPIC_API_KEY`, never the signed-in subscription.
  - Its environment is the CLI's own minus `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN`. Claude Code prefers an API key it finds over the signed-in subscription, so leaving either in would bill the run to the API.
- `prompt.md` gains a `{{tools}}` placeholder, the paragraph about tools and checks. For agent runs it is today's text: no shell, and `run_checks` is the only way to run the checks. For session runs it says to run the checks with `npm run check`, which is the only command allowed. Steps 1 to 3 of the brief and the other rules are shared.
- The session's JSON result maps to `AgentRun`: `structured_output` validated with `AgentReportSchema`, `num_turns` as turns, `duration_ms` as the duration, and `total_cost_usd` as the cost. Claude Code computes that cost at list prices whatever the account is billed, so the PR footer labels it `est.` for session runs. `is_error` true, a `subtype` other than `success`, or a missing or invalid `structured_output` throws `Agent stopped without finishing: <subtype>` or `Agent report did not match the schema: <reason>`. Those are the messages `classifyFailure` already maps to `agent-stopped` and `bad-report`.
- **Limits.** Claude Code's print mode has no turn limit, so `--max-turns` is a usage error with `--session`, and `--max-minutes <n>` (default `60`, validated with `parseLimit(…, { integer: true })`) bounds the session's wall-clock time. When it runs out, the harness kills the session and throws `Agent stopped without finishing: timed out after <n> minutes`. `--max-budget` is passed as `--max-budget-usd`, a cap on Claude Code's own estimate.
- The CLI checks `claude --version` before the preflight and stops with `Claude Code (claude) is not installed or not on PATH.` if it fails. A session run needs no `ANTHROPIC_API_KEY`.
- **Branch and PR.** A session run works on `spec/<slug>`, the prefix for code a Claude Code session wrote: `branchName(spec, kind)` takes `"agent"` or `"session"`. Its commit body says `Implements <spec path> in a headless Claude Code session.`, and its PR body opens with `> Implemented in a headless Claude Code session from \`<spec path>\`. A human reviews and merges.` The `Agent-Run` trailer and the audit log work as for an agent run. The log gets the session's command line (minus the prompt, which is logged on its own) as `session.start`, and its JSON result as `session.end`.
- `--session` can't be combined with `--fix-pr` or `--plan` (a wave passes it to its runs itself).

### Claiming a spec before the code is written
- `GitOps` (in `spec-coding-agent/src/pipeline.ts`) gains `claimBranch(name: string): Promise<unknown>`. `Git` implements it as `git push --porcelain --no-verify --force-with-lease=<name>: origin <name>`, and throws unless the porcelain status line for `refs/heads/<name>` starts with `*` (created). The empty expected value means "this ref must not exist on `origin` yet", and the server checks it. Git skips that check when `origin` already has the branch at the same commit and reports `[up to date]` with exit code 0. Two runs started from the same `main` claim at exactly the same commit, so a claim must see `*`.
- `GitOps` also gains `branchExistsOnOrigin(name: string): Promise<boolean>`: the exact-match `git ls-remote --heads origin refs/heads/<name>` check that `Git.branchExists` already makes, on its own. It throws if `ls-remote` fails, so an unreachable `origin` is never read as "no branch".
- **A spec has two branch names**, `agent/<slug>` and `spec/<slug>`, and a run of either kind holds both:
  - Preflight fails with the ordinary `Branch … already exists` error when either exists, locally or on `origin`.
  - `runPipeline` calls `claimBranch(branch)` right after `createBranch` and before `fingerprint()` and the code-writing step. Dry runs don't claim. Once the claim succeeds, it checks the other name with `branchExistsOnOrigin`. If that exists too, a run of the other kind claimed in the same seconds, and the run throws a `ClaimLostError`. In that exact race both runs may stop, which is safe: a false alarm, never two implementations.
- **A branch can't tell a live claim from a stale one.** A run that claims and then fails leaves its branch on `origin` with nobody working on it, and nothing in the branch says so. So whenever the state is ambiguous, the run fails loudly, and a person decides, as spec 005 does for every exception. Only a lost race is unambiguous:
  - **A lost race:** `claimBranch` fails and `branchExistsOnOrigin(branch)` is then true, or the other name exists on `origin` after a successful claim. `runPipeline` throws a `ClaimLostError` (a new exported `Error` subclass in `pipeline.ts`) with the message `Another run already claimed <spec path>: <branch> exists on origin.`, naming the branch it found, before the code-writing step starts.
  - **Any other failed claim push** (credentials, network, permissions, a server hook, or `branchExistsOnOrigin` throwing or returning false): `runPipeline` rethrows the push's error unchanged, as an ordinary failure.
- `exitCodeFor(error: unknown): number`, exported from `pipeline.ts`, returns `3` for a `ClaimLostError` and `1` for anything else. The CLI exits with it, and the run log's `run.end` gets the category `claim-lost`. `npm run agent` passes the code through the root script's nested `npm start -w`. Only local waves act on `3`. CI doesn't map it: a CI run that loses a race fails and shows as `needs-human: failed`.
- The claim branch points at the base commit, so it holds none of the run's work until the final push, which fast-forwards it. If the run fails after claiming, the branch stays on `origin`, spec 005's rules show the spec as `in-progress (<branch>)` (or `needs-human: failed` for a CI run), and any retry fails at preflight until a person deletes the branch.
- A branch on `origin` can be another run's live claim. So the README's re-arm steps say to delete one only after `--plan` shows the spec with no open PR and no run in flight, and only on the machine whose wave kept the worktree.
- `Git.push` drops `-u`: `git push --no-verify origin <branch>`. Parallel worktrees share the main repository's config, and `-u` writes tracking keys into it, which would change the git-state fingerprint of every other run in progress and fail them. The fix cycle's pushes go through the same method.

### Starting from a detached worktree
- `runPipeline`'s preflight also accepts a detached `HEAD` whose commit is on `origin/<base>`: equal to it or an ancestor of it. Worktrees can't check out `main` while the main checkout has it, and a `git fetch` anywhere in the repository moves the shared `origin/main` ref while a wave's other worktrees are still preparing.
- `GitOps` gains `headSha(): Promise<string>`, which `Git` already has, and `headOnBase(base: string): Promise<boolean>`. `Git` implements it as `git merge-base --is-ancestor HEAD refs/remotes/origin/<base>`: exit code `0` is true, `1` is false, and anything else throws with the output. A detached `HEAD` that isn't on `origin/<base>` throws `Check out <base>, or detach on origin/<base>, first (currently detached at <short sha>).` A named branch behaves exactly as today.

### Planning with local worktrees
- New module `spec-coding-agent/src/local.ts`. Worktrees for local runs live in `<worktreeDir>/<slug>`. The CLI default for `worktreeDir` is `<parent of the repo root>/<repo folder name>-worktrees`: outside the repository, and outside the system temp directory, because a kept worktree is the record of a failure.
- `SpecState` (in `coordinate.ts`) gains `{ status: "needs-human"; reason: "local-worktree"; worktree: string }`, and `formatPlanned` prints it as `needs-human: local-worktree (<path>)`.
- `applyLocalWorktrees(plan, worktrees, worktreeDir, platform = process.platform)` is pure. A spec has a leftover worktree when the resolved `worktreeDir` plus `slug` equals the resolved path of one of `worktrees`, with the path functions of `platform`: `path.win32.resolve` and lowercased for `win32`, `path.posix.resolve` otherwise. Such a spec becomes `needs-human` / `local-worktree` when its planned state is `ready`, or `in-progress` with only a `branch`. Every other state is kept: GitHub's view wins once a PR or a run exists.
- `worktrees` comes from `git worktree list --porcelain`, run right after `git worktree prune`: the path of each `worktree <path>` line.

### A local wave
- `runLocalWave(deps)` takes the parsed specs, an injected `Exec`, the repo root, `worktreeDir`, `maxParallel`, the run arguments to pass on (`agentArgs: string[]`), the environment for the runs (`env`), an injected `spawnAgent`, an optional sandbox preparation step, `log` and an optional `RunLog`. It returns `{ plan, started, succeeded, lostClaim, failed: { spec, worktree, exitCode }[] }`. In order:
  1. **Checkout.** The same checks as `--dispatch`: `git fetch origin main`, `HEAD` equals `origin/main`, nothing uncommitted under `specs/`.
  2. **Lock.** It creates `worktreeDir` if missing, resolves it with `fs.realpath`, and uses only that real path from then on. Then it creates `<worktreeDir>/.lock` with the `wx` flag and removes it in a `finally`. Only `EEXIST` means another wave holds it; it then throws `Another local wave is running, or one crashed and left <path>; delete it if none is running.` Any other error propagates.
  3. **Plan.** The same three GitHub reads as `runCoordinator`, through an exported `readGithubState(exec, repoRoot)` in `coordinate.ts` that `runCoordinator` uses too, then `planSpecs`, then `applyLocalWorktrees`. It logs one `formatPlanned` line per spec.
  4. **Prepare.** It takes up to `maxParallel` `ready` specs, lowest number first. For each, in turn: `git worktree add --detach <worktreeDir>/<slug> origin/main`, then `npm ci` in it with a 15-minute timeout. With a Docker sandbox it prepares the sandbox once, before any run starts. If preparing fails, it removes every worktree it created in this wave with `git worktree remove --force <path>`, logging a failed removal instead of throwing, then throws naming what failed, before any run starts.
  5. **Run.** It starts every prepared spec at once with `spawnAgent(["<spec path>", "--session", ...agentArgs], { cwd: <worktree>, env: { ...env, INIT_CWD: <worktree> }, onLine })`, which resolves to a numeric exit code, and waits for all of them. Each output line goes to `log` prefixed with `[<number>] `. One run failing doesn't stop the others.
  6. **Clean up**, by exit code:
     - `0`: `git worktree remove <worktree>`. On failure it logs a warning naming the path to remove by hand.
     - `3`, a lost claim: the worktree holds no work, and its local `spec/<slug>` branch points at the base commit. It runs `git worktree remove --force <worktree>` and `git branch -D spec/<slug>`, logging rather than throwing on failure, and records the spec in `lostClaim`.
     - Anything else: it keeps the worktree, records the spec in `failed`, and logs the worktree path.
- `spawnAgent`'s default runs `npm run agent -- <args>` through an exported `spawnLines(command, args, options)`, which streams stdout and stderr line by line and resolves to `childExitCode(code, signal)`: the code when it is a number, `1` when the child was killed by a signal or couldn't start. Like `exec`, it uses a shell only for `npm` on Windows, with every argument quoted by an exported `cmdArg`, which refuses `"`, `%`, `!` and line breaks and doubles trailing backslashes inside quotes.
- With a `RunLog`, it logs `plan.result`, then a `local.start` event `{ spec, worktree }` per run started and a `local.end` event `{ spec, worktree, exitCode, kept }` per run finished.

### CLI
- New option `--local`: `npm run agent -- --plan --local [--max-parallel <n>] [--worktree-dir <dir>] [run options]`, listed in `USAGE`.
  - It reads the specs and runs `checkSpecs` as `--plan` does, checks `claude --version` as a session run does, then calls `runLocalWave`.
  - `--max-parallel`: default `2`, validated with `parseLimit(…, { integer: true })`. `runLocalWave` also throws `RangeError` for a `maxParallel` that isn't a positive integer.
  - `--local` without `--plan`, `--local` with `--dispatch`, `--worktree-dir` without `--local`, and `--max-turns` with `--local` are usage errors.
  - It needs no `ANTHROPIC_API_KEY`. The `env` it passes to `runLocalWave` is its own `process.env` minus `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN`.
  - It passes these options to every run unchanged: `--scope`, `--model`, `--effort`, `--max-minutes`, `--max-budget`, `--sandbox`, `--sandbox-image`, `--standards`, `--standards-packs`, `--standards-ref`, `--max-standards-chars`. `--log-dir` goes as an absolute path, so every run's audit log lands in one folder. Relative paths in the other options resolve in each worktree, which is at `origin/main`.
  - Parallel sessions share the subscription's usage limits. The process exits non-zero when any run failed; a lost claim alone doesn't count.

## Acceptance criteria
- AC1: `runPipeline` accepts a detached `HEAD` for which `headOnBase` is true and creates the branch as usual. It throws the detached-`HEAD` message when `headOnBase` is false, and behaves as before on a named branch: it runs on `base` and throws on any other branch.
- AC2: On a non-dry run, `runPipeline` calls `claimBranch` after `createBranch` and before `fingerprint` and the code-writing step. When `claimBranch` rejects and `branchExistsOnOrigin` is then true, or when the claim succeeds and the other branch name exists on `origin`, it throws a `ClaimLostError` naming the spec and the branch it found, and never runs the code-writing step. When `claimBranch` rejects and the branch isn't on `origin`, or `branchExistsOnOrigin` throws, it rethrows the push's error unchanged and never runs that step. Either branch name existing at preflight, on `origin` or locally, gives the ordinary `already exists` error. `exitCodeFor` returns `3` for a `ClaimLostError` and `1` otherwise. A dry run never calls `claimBranch` or `push`. `Git.claimBranch` and `Git.push` run exactly the arguments above, with no `-u`, and `claimBranch` fails on a `[up to date]` status.
- AC3: In a real temporary repository with a local bare `origin` and two worktrees, both detached on `origin/main`:
  - the first `claimBranch` for a branch succeeds, and a second one, from the other worktree at the same commit, fails;
  - `createBranch`, `claimBranch` and `push` in worktree A, taken together, leave worktree B's `fingerprint()` unchanged;
  - `headOnBase` is true for a commit behind `origin/main` and false for a commit that isn't on it.
- AC4: `applyLocalWorktrees` turns a `ready` spec, and an `in-progress` spec with only a branch, into `needs-human` / `local-worktree` when its worktree is listed. With `platform: "win32"`, on any host, forward slashes match backslashes and letter case doesn't matter, drive letter included. With `platform: "linux"`, case matters. It leaves specs with an open PR, a merged PR, an in-flight run or no worktree unchanged. `formatPlanned` prints the new state as specified.
- AC5: With a fake `Exec` and a temporary `worktreeDir`, `runLocalWave` creates a missing `worktreeDir` before taking the lock; uses the real path of a `worktreeDir` that is a directory symlink (a junction on Windows); throws before creating any worktree when `HEAD` isn't `origin/main`, when `specs/` has uncommitted changes, or when the lock file exists (the "another local wave" message only in that case); throws `RangeError` for a `maxParallel` of `0`, `-1` or `1.5`; and removes its lock file after a wave that succeeds and after one that throws.
- AC6: For three `ready` specs and `maxParallel: 2`, `runLocalWave` prepares and starts only the two lowest. It runs `git worktree prune` before `git worktree list --porcelain`, and the exact `git worktree add` and `npm ci` commands for each spec. It prepares the sandbox once before the first `spawnAgent` when one is given. It calls `spawnAgent` with the spec path, `--session` and `agentArgs`, the worktree as `cwd`, and an `env` that keeps the given variables and sets `INIT_CWD`. When `npm ci` fails for the second spec, it removes both worktrees with `git worktree remove --force`, throws naming that spec, and never calls `spawnAgent`.
- AC7: For three runs that exit `0`, `1` and `3`, `runLocalWave` removes the first worktree; keeps the second and returns it in `failed` with its worktree and exit code; and for the third runs `git worktree remove --force` and `git branch -D spec/<slug>` and returns it in `lostClaim`. It logs every output line with its `[<number>] ` prefix, and with an in-memory `RunLog` one `local.start` and one `local.end` per run, `kept` true only for the failure. `childExitCode` returns the code for `(0, null)` and `(1, null)`, and `1` for `(null, "SIGTERM")` and `(null, "SIGKILL")`. `spawnLines`, run against real `node` children, streams stdout and stderr lines and resolves to their exit codes, and to `1` for a command that can't start. `cmdArg` quotes, refuses and doubles trailing backslashes as specified.
- AC8: With an injected spawn, `runSession`:
  - runs `claude` with exactly the arguments above, in the repo root, never with `--bare`, and with an environment that has neither `ANTHROPIC_API_KEY` nor `ANTHROPIC_AUTH_TOKEN`;
  - turns a successful result into an `AgentRun` with the validated report, `num_turns`, `duration_ms` and `total_cost_usd`;
  - throws the `agent-stopped` message for `is_error`, a non-`success` subtype or a timeout (and kills the session on timeout), and the `bad-report` message for a missing or invalid `structured_output`.
  `buildPrompt` fills `{{tools}}` with the agent text or the session text. A session run's branch is `spec/<slug>`, and its commit body, PR opener and `est.` cost label are as specified. `--session` with `--fix-pr` or `--plan`, `--max-turns` with `--session` or `--local`, and `--max-minutes` that isn't a positive integer are rejected.
- AC9: `spec-coding-agent/README.md` documents session runs (`--session`, what runs them, the subscription and its usage limits, the tools allowed, `--max-minutes`, what the code gates still enforce, and what a session's own `npm run check` exposes); the early claim on both branch names, and that only a lost race gives exit code `3` and `claim-lost`; `--plan --local` and its options; the worktree folder, the `local-worktree` state, and that a lost claim removes its worktree; re-arming a local failure (`git worktree remove`, or `git worktree prune` when the folder is gone, delete the local branch, check with `--plan` that no PR is open and no run is in flight before deleting the `origin` branch, then run again); and that interrupting a wave leaves its worktrees, claim branches and lock behind.

  Tests use fakes, except AC3's repository and AC7's `node` children in temporary directories, like the existing `git-repo.test.ts`. No network, no `gh`, no `claude`, no Anthropic calls.

## Out of scope
- API-billed agent runs in a local wave. CI and plain `npm run agent` runs keep using the Agent SDK and the API.
- A session run's own checks in the Docker sandbox. The session runs `npm run check` on this machine, as `/code-spec` session mode does; `--sandbox docker` covers the harness's re-run of the checks.
- Capturing the session's full transcript in the audit log (`--output-format stream-json`).
- `--fix-pr` with `--session`: the fix cycle for a session PR stays `/fix-review`.
- Changes to the `/code-spec` and `/fix-review` skills.
- Starting another wave automatically when a wave finishes, cleaning up after Ctrl-C, or removing kept worktrees and claim branches automatically.
- Showing a local failure on other machines or in CI. There the spec shows `in-progress (<branch>)` until a person re-arms it.
- Sharing `node_modules` between worktrees, or running `npm ci` in parallel.
- Changes to spec 005's state rules other than the `local-worktree` state.
- Treating exit code `3` as success in `implement-spec.yml`.
- Claims that expire (leases, heartbeats), which would let the coordinator tell a stale claim from a live one.
